Purpose

The query engine is the second half of psxGPT. It takes a human question, turns it into a search plan, retrieves structured rows and document evidence, recovers source links, and writes an answer from that evidence. It is only useful because the pipeline already preserved rows, page text, and links back to the source PDF.

The answer has a trace

Every answer has working files behind it: planner output, SQL, returned rows, retrieved pages, source links, and analyst context. When an answer is wrong, the trace tells you where to look first.

The source panel matters

The user can open the filing page behind a number or claim. The answer is a starting point for verification, not a substitute for it.

Usage finds the misses

A real query exposes planner mistakes, missing rows, weak retrieval, or unsupported answers. Those failures become evaluation cases so the same mistake is easier to catch next time.

The engine is not allowed to invent missing data. It can only retrieve, compute, cite, and explain what the pipeline has written into the SQLite database and document index.

Where the pipeline ends and the engine begins

The pipeline runs once per filing and writes rows to the SQLite database. The engine runs for every user query and reads from it. They share no code and no context. The SQLite schema and source-link fields are the contract between them. If a number is wrong in the database, no amount of prompt engineering in the engine can honestly fix it.

Ingestion Boundary

The first debugging question is simple: is the right data in the SQLite database? If not, the issue belongs to the pipeline. The query engine should not compensate for a broken database layer.

SymptomFirst checkLikely layer
Expected number absentRun direct SQL against the SQLite database for ticker, field name, and period.Pipeline if the SQLite database has no row.
Wrong value returnedTrace row to source page and extracted JSON.Pipeline if the SQLite database value is wrong.
Correct value in the SQLite database but not in answerInspect the generated SQL and working file rows.Engine search step or planner.
Correct evidence retrieved but bad answerInspect analyst context and prompt.Analyst instruction or context assembly.

What the database row looks like — the end product of the pipeline

Source page: Consolidated Statement of Financial Position, LUCK Annual 2024, page 287. Total assets: 659,661,625 PKR '000. This page was located by the pipeline locator, extracted, QC'd, and written to the database as flat rows.

What the database holds — financial_statements rows

SELECT ticker, period, section,
       field_name, value, unit_type
FROM financial_statements
WHERE ticker = 'LUCK'
  AND period = '12M Jun 2024'
  AND statement_type = 'BS'
  AND section = 'consolidated'
  AND field_name = 'total_assets';

-- Returns:
ticker  | LUCK
period  | 12M Jun 2024
section | consolidated
field   | total_assets
value   | 659661625
unit    | thousands
pages   | ["LUCK/2024/...page_287.pdf"]

The source_pages column is how the engine recovers the PDF link without re-running extraction. If this row is missing or wrong, the engine cannot fix it — that is a pipeline problem.

Do not update planner or search prompts until the SQLite database confirms the data exists and is correct. Otherwise the prompt fix becomes a data-quality band-aid.

1. Planner

A user question usually compresses several decisions: company, period, metric, comparison set, source type, and sometimes an implied calculation. The planner expands that compressed request into a step-by-step evidence plan. It should decide what to retrieve, not retrieve it itself.

Planner outputPurposeFailure
tableWhich source should answer: financial statements, ratios, market data, management comp, or documents.Wrong table means all later evidence is misdirected.
tickers / scopeNamed companies, industry universe, market-wide screen, or selector dependency.Missing scope causes empty or overbroad retrieval.
metricsStandard field names, ratio names, or narrative concepts.Wrong field name or synonym gap.
timePeriod end, latest N periods, annual/quarterly duration.3M vs 12M mistakes and misleading trends.
dependenciesOne search feeding another, e.g. find top banks first, then retrieve sector exposure for those banks.Question answered as one flat search instead of two-stage computation.

Example planner output

{
  "steps": [
    {
      "id": "step_1",
      "table": "financial_statements",
      "tickers": ["LUCK", "MLCF", "CHCC"],
      "metrics": ["revenue_net", "gross_profit", "net_profit"],
      "time": { "duration": "12M", "periods": "latest_2" },
      "purpose": "Compare cement sector P&L across the three largest players"
    },
    {
      "id": "step_2",
      "table": "ratios",
      "tickers": ["LUCK", "MLCF", "CHCC"],
      "metrics": ["gross_margin", "net_margin", "return_on_equity"],
      "time": { "duration": "12M", "periods": "latest_2" },
      "depends_on": "step_1",
      "purpose": "Compute margin ratios using rows from step_1 as denominator check"
    }
  ]
}

A two-step plan: structured data first, then ratios derived from it. The planner declares intent; the search step does the SQL. If the planner routes a metric question to "documents", every downstream step is looking in the wrong place.

2. Structured Search Steps

Structured search steps run SQL against the SQLite database and return evidence only when the result covers the required companies, periods, and fields. This is where the plan becomes a bounded working file: SQL, rows, coverage, and diagnostics.

Financial statements

Uses financial_statements rows keyed by field name, period, section, and ticker.

Ratios

Uses precomputed metrics. Source links are recovered through component statement rows when possible.

Market data

Uses trading data with staleness guards so suspended or stale tickers do not dominate screens.

Management comp

Uses structured compensation rows and links back to filing pages through source URLs.

Search steps can iterate, but they must eventually produce a bounded working file: final SQL, rows, coverage status, and diagnostics. That file is what the reviewer and evaluations inspect.

3. Narrative Retrieval

Narrative retrieval handles questions that cannot be answered from rows alone: risks, strategy, segment detail, charts, notes, and management commentary. It searches over search_text and markdown-derived document rows created by the pipeline.

ElementPurpose
keyword search queryCheap lexical retrieval over page-level search_text.
Ticker/filing filtersKeep retrieval scoped to the companies and periods in the ask.
Balanced retrievalPrevent one ticker from consuming all top results in multi-company asks.
Coverage validationReject narrative submits that do not cover required tickers or concepts.
Optional page extractionExtra enrichment only. It should not block the search step from returning its core evidence.

Why search_text beats raw markdown for retrieval

Some pages have real financial data that OCR cannot read — charts, scanned images, figures embedded as images. Raw markdown BM25 would miss any query about the content of those pages. The pipeline generates a search_text field by reading the page with a small model, which can surface key terms even when the markdown is sparse.

Raw page markdown — what BM25 would index

<!-- Page 13 -->

# Key Highlights for the Year
  (Unconsolidated)

![img-21.jpeg](img-21.jpeg)
![img-22.jpeg](img-22.jpeg)
![img-23.jpeg](img-23.jpeg)
![img-24.jpeg](img-24.jpeg)
![img-25.jpeg](img-25.jpeg)
...nine total image references

A query for "earnings per share trend" or "EPS FY20 to FY24" would not match this page at all. BM25 over raw markdown fails here.

Generated search_text — what BM25 actually indexes

Key Highlights for the Year, unconsolidated,
Net Revenue trend FY20-FY24, EBITDA growth,
Profit Before Tax FY24 40.4 billion, Profit
After Tax 28.1 billion, Earnings Per Share
94.54 rupees, Book Value Per Share, Market

234 billion, Capital Expenditure, CSR
Expenditure, six-year financial summary

The same query now matches. The pipeline spent one model call per page at ingestion time so the engine can search cheaply at query time — many times, for many users.

Keyword search works because the pipeline invested in page-level search_text. The engine should use that inspectable representation before reaching for heavier retrieval designs like embeddings or per-query page extraction.

4. Source Links Recovery

Structured SQL returns numbers, not page previews. Source-link recovery maps rows back to filing pages so the UI can show the source behind the answer.

Data typeHow source links are recoveredUsed by analyst?
Financial statementssource_pages plus ticker/filing lookup into document rows.No. Analyst sees the computed table.
RatiosMap ratio to component statement fields, then recover statement source pages.No. Analyst sees ratio table.
Management compSource URL/page metadata lookup.Usually through structured table; pages go to panel.
Narrative search stepDocument IDs selected by keyword search.Yes, capped and assembled into analyst context.

5. Analyst Assembly

The analyst receives a capped evidence package. Its job is to synthesize retrieved evidence, explain uncertainty, and cite sources. It should not fill gaps by inference or override retrieved evidence because the prose sounds right.

What the analyst context contains

User query
"Compare LUCK and MLCF gross margins for the last two years and explain any divergence."
Structured tables — from search steps
financial_statements rows for revenue_net, cost_of_revenue, gross_profit for both tickers, 12M Jun 2024 and 12M Jun 2023. Computed gross_margin ratio table. Coverage confirmed: 2 tickers × 2 periods × 3 fields = 12 rows present.
Narrative pages — capped, from keyword search
Up to N pages from MD&A sections for LUCK and MLCF discussing cost pressures, fuel costs, capacity utilization. Balanced retrieval: no single ticker dominates.
Instructions
Citation format. Unit declaration (PKR thousands). Uncertainty language when evidence is incomplete. Do not recalculate values not present in retrieved rows.

What the analyst should do

Synthesize retrieved evidence, explain computed results, cite sources, and state uncertainty when evidence is incomplete.

What the analyst should not do

Invent missing rows, recalculate unsupported values from thin context, or override retrieved evidence because the prose sounds plausible.

6. Source Panel

The source panel is broader than the analyst context. It exists for user inspection and debugging, not only answer synthesis. A page can be useful to the reviewer even if it was not necessary to put the entire page into the analyst prompt.

SurfaceWhat it containsWhy separate?
Analyst contextCapped narrative pages plus structured data tables.Keeps answer generation focused and affordable.
Source panelNarrative pages plus structured source links pages.Lets users inspect backing pages even if analyst did not read every page.
Search working filesSQL, rows, tool history, diagnostics.Developer debugging and evaluation review.

Context Buckets

The engine is easier to debug when stable facts, model instructions, and code checks are kept separate. Facts tell the model what exists. Instructions tell it how to behave. Code enforces rules that should not depend on model obedience.

BucketExamplesFix here when
Fact Table shapes, field-name inventories, ratio names, allowed planner fields, keyword search vocabulary notes. The model is missing or misusing true database facts.
Instruction Planner rules, SQL strategy, narrative retrieval playbooks, analyst citation rules. The facts are correct but the model chooses the wrong behavior.
Code SQL execution, validation, source-link recovery, context caps, working file assembly. A behavior should be enforced deterministically for every query.
Prompt fixes that belong in code. If a rule must hold for every query regardless of phrasing — ticker coverage, context caps, period validation — it belongs in code, not in the system prompt. A model that usually follows an instruction is not the same as code that always enforces it.

Code Checks

Some rules should live in code because they should always run the same way. These checks reduce cognitive load by preventing whole classes of obvious mistakes before the analyst model ever sees context.

Code checkReason
Reject global latest-period SQL for named multi-ticker comparisons.Prevents one ticker's latest period from being applied to all tickers.
Require ticker coverage before a structured search returns.Prevents silent dropping of companies in compare/trend asks.
Short-circuit out-of-universe tickers.Avoids wasted model calls and makes unsupported symbols explicit.
Separate source panel from analyst context.Prevents context bloat while preserving inspectability.
If a rule is only correct for one query type, it belongs in instructions or nowhere. Code checks must be broadly correct.

Debugging

Debug from the database upward. The symptom appears in the answer, but the fix is often lower: missing row, wrong source link, bad SQL, weak retrieval, or only then a bad analyst instruction.

1
Reproduce the query in the notebook

Run the exact query that produced the wrong answer. Capture the full working file: planner plan, search steps, analyst context, final output.

2
Check the SQLite database directly

Run SELECT * FROM financial_statements WHERE ticker=? AND field_name=? AND period=?. If the row is missing or wrong, the problem is in the pipeline — stop here and go to the pipeline guide.

P
If data is absent or wrong → pipeline

Trace backward: flat rows → extracted JSON → canonical markdown → OCR markdown → source PDF page. Fix the lowest broken step. Do not touch engine prompts.

E
If data is correct → engine search step

Inspect planner output and each search working file. Check SQL generated, rows returned, coverage status. If the SQL is wrong, fix the planner fact or instruction.

A
If evidence is correct → analyst

Inspect what was assembled into analyst context. If the right rows are there and the answer is still wrong, fix the analyst instruction. This is the last layer to touch.

★
Convert the failure into an evaluation case

Every diagnosed failure is a free gold case. Add it to the eval set so the same class of mistake is caught automatically next time.

SymptomLikely fix
Planner emits wrong table.Metric routing fact or planner instruction.
Search step writes the wrong field name or enum.Fact file if the database shape changed; instruction if strategy is wrong.
Narrative search step retrieves irrelevant pages.Keyword search vocabulary inventory or narrative search instruction.
Analyst overclaims.Analyst prompt only after retrieved evidence is confirmed correct.
Source panel missing structured pages.Source-link recovery logic or missing source_pages in the SQLite database.

Evaluations

Query evaluations protect the engine against regressions and convert real failures into reusable tests. They are how usage turns into improvement instead of one-off debugging.

Retrieval evaluations

Did the search steps retrieve the expected rows/pages?

Faithfulness evaluations

Did the analyst only claim what the evidence supports?

Source evaluations

Did the source panel surface the right filing pages?

Routing evaluations

Did the planner split the question into the right search steps?

Run targeted evaluations after a fix, full evaluations periodically, and update gold cases when a production failure reveals a new class of mistake.

Prototype to system

Building a demo that answers questions from documents takes a week. Making that demo reliable takes months. The gap between the two is what this course is about.

An LLM handles the extraction, a retrieval step finds the relevant pages, a synthesis step produces an answer. The demo impresses. Then you put it in front of real users and the problems appear: a number that came from the wrong period, an answer that cites a page it never read, a schema that worked on the first ten documents and breaks on the eleventh. None of these failures announce themselves. They look like correct output.

The prototype is not the system

A working demo proves the approach is viable. It does not prove the output is correct. Correctness requires surfaces — places where a human or an automated check can verify that what the system returned matches what the source document actually says.

Traceability is the foundation

Every answer must carry a citation: which document, which page, which line. Every stage must write a file that can be inspected. Without these surfaces the system cannot be audited, cannot be debugged, and cannot be improved — you can only guess at what went wrong.

The schema will be wrong at first — that is expected

The data model you design before seeing real usage will not survive contact with real usage. Fields will be missing, types will be wrong, edge cases will appear that the schema does not handle. The methodology is built for iteration: every stage writes a file, every file can be re-generated, and changing one stage does not require rebuilding the others. Usage tells you what the schema actually needs to be. You build toward that incrementally.

This course does not teach you to build a demo. It teaches you to build a system — one that is inspectable when something goes wrong, and improvable without breaking what is already working.

Two systems, one database

The approach splits into a pipeline and an engine. They share one database. The pipeline's job is to produce data the engine can trust. The engine's job is to answer questions with citations.

SystemInputOutputPrimary concern
Pipeline Raw PDFs Structured rows + source page links in SQLite Correctness of extracted values and completeness of citations
Engine A natural-language question A structured answer with source citations Relevance of retrieved evidence and faithfulness of the answer to that evidence

The pipeline writes two tables: financial_statements (one row per metric per period) and financial_documents (one row per page, with OCR text and metadata). The engine reads both. A ratio question uses financial_statements. A question that requires reading a note or a management comment uses financial_documents.

The split is intentional. Structured data answers structured questions precisely. Unstructured document pages answer open-ended questions with source context. Conflating them produces a system that does neither well.

When to spend compute

Every stage of the pipeline has a cost. The discipline is to spend as little as possible at each stage — run the cheap check first, escalate to the expensive one only when the cheap check cannot decide.

Free deterministic
Regex, structural checks, keyword gates — runs on every page, no API call
Free
Cheap LLM
Single-turn classification or short extraction — fast, low token count
Low
Medium LLM
Extraction with full page context, repair calls on flagged pages
Medium
Expensive multi-turn
Multi-step reasoning, large context windows — reserved for the engine only
High

The pipeline spends compute only on pages that survive the preceding gates. A page that is deterministically identified as a table of contents never reaches the classifier. A page that the classifier rejects with high confidence never reaches the extractor. Spend accumulates only at the stages where it is genuinely needed.

Working files are the control points

Every stage writes a file. That file is the contract between that stage and the next. It is also the primary debugging surface — when something goes wrong, the file shows exactly what the stage decided and why.

Routing files

Decide which pages go to which stage next. The skip manifest, classification manifest, and extraction manifest are routing files. They contain no content — only decisions.

stage1_qc.json, stage2_classification.jsonl

Product files

The output the next system will actually use. Flat financial statement rows, compiled document pages, the SQLite database. These are the deliverables.

stage5_flat_*.jsonl, psxgpt_course.db

Diagnostic files

Explain why a page failed a check or was routed to repair. Not consumed downstream — read by a human debugging an anomaly.

repair_manifest.json, qc_failures.json

Gold files

Manually verified correct outputs for a sample of documents. Used to evaluate the pipeline and catch regressions when a stage is changed.

gold_classification.json, gold_extraction.json

Because each stage reads a file and writes a file, any stage can be re-run in isolation. If the classifier changes, only the files downstream of classification need to be regenerated. Earlier stages are unaffected.

Fact, instruction, code

Every prompt is built from three types of content. Keeping them separate is not style — it is the mechanism that makes prompts debuggable and improvable without side effects.

Fact

The data the model needs to do its job: the page text, the metadata, the prior outputs. Facts change with every document. They should never be embedded in the instruction text.

Instruction

What the model must do, and the standards it must meet. Instructions change rarely — only when the task definition itself changes. They should be versioned and tested independently.

Code

The output format: JSON schema, field names, required keys. Code changes when the downstream consumer changes. Keeping it separate makes schema migrations visible.

When an extraction fails, this separation tells you where to look. A wrong value with a correct structure is a fact problem or an instruction problem. A correct value with a wrong structure is a code problem. You do not need to read the whole prompt to diagnose the failure.

Two quality check loops

Quality is maintained by two loops that operate at different speeds and catch different classes of error.

The fast loop — deterministic, runs on every document

Structural checks that can run without any model call: do the columns add up, are required fields present, are values within plausible ranges, are source page links intact? The fast loop runs in milliseconds and produces a pass/fail routing decision for every row. A row that fails goes to repair or is flagged for review — it does not enter the database.

The slow loop — sampled, runs on batches

Human review of a sample of outputs compared against gold sets. The slow loop catches errors the fast loop cannot detect: a structurally valid but semantically wrong extraction, a figure that is arithmetically plausible but factually incorrect. Run it before deploying a changed stage, and run it periodically on production outputs.

A system with only a fast loop will confidently produce wrong answers that pass every check. A system with only a slow loop will catch errors too late. Both loops are required.

Evaluations and gold sets

Each LLM stage needs a gold set: a small, manually verified dataset that defines what correct output looks like for that stage. Without gold sets, you cannot tell whether a change improved the system or just changed it.

StageWhat the gold set containsHow it is used
Classification Pages labeled by hand with their correct type Measures classifier accuracy; catches regressions after prompt changes
Statement page locator The correct statement pages for a sample of filings Measures whether the right pages are routed to the right extractor
Extraction Correct financial values with their source page citations Measures extraction accuracy and citation completeness
Query engine Questions with correct answers and source references Measures answer faithfulness, retrieval precision, and citation accuracy

Gold sets do not need to be large. Ten to thirty examples per stage are enough to catch systematic failures. The discipline is to add a case to the gold set every time a real-world failure is found and fixed — so the fix is tested permanently.

Fix in order

When something is wrong, there is a correct order of diagnosis. Skipping steps wastes time and produces fixes that break at the next document.

OrderWhat to checkWhy first
1 The source data If the input document is corrupt, unreadable, or formatted unusually, no amount of prompt tuning will produce correct output. Confirm the source is valid before touching the pipeline.
2 The routing files If the right pages are not reaching the right stage, the extractor has nothing correct to work with. Check the manifests before assuming the extraction is wrong.
3 The prompt facts Confirm that the correct page text and metadata are being passed to the model. A wrong fact in the prompt produces a wrong answer that looks like a model failure.
4 The instructions Only if source, routing, and facts are all correct should you change the instruction. At this point you know the model is receiving everything it needs and is still producing the wrong output.

Where prompt optimizers fit

Prompt optimizers — tools that automatically tune instruction text against a metric — are useful, but they operate at step four of the fix order. They cannot compensate for bad source data, wrong routing, or incorrect gold sets.

An optimizer that is given a bad gold set will learn instructions that produce the wrong answers the gold set calls correct. An optimizer that is given good gold but bad source data will learn workarounds that pass the evaluation but fail on the next real document.

Use optimizers after the system is already producing mostly-correct outputs on good inputs. Their role is refinement, not foundation.

The sequence is: build correct working files, build correct gold sets, run the slow loop to verify the system is mostly right, then use an optimizer to close the remaining gap on the instruction text.

The course

The course applies this methodology to a concrete problem: making Pakistani equity filings queryable with source-linked answers. Every principle above is visible in the implementation. The skills transfer to any corpus.

There are two modules, each with a dedicated guide. Work through them in order.

1

Pipeline — from PDF to structured database

You will run an eight-stage pipeline that takes raw company filings and produces normalised financial statement rows and document pages in SQLite. Every stage writes a file you can inspect. Every LLM call has a seeded output so you can study the result without cost. The pipeline is the foundation — without correct structured data, the engine cannot give correct answers.

2

Engine — from question to source-linked answer

You will build a query engine that takes a natural-language question, retrieves relevant rows and document pages, and returns a structured answer with citations. The engine reads the database the pipeline produced. The two systems are independent — changing one does not require changing the other — but they are designed to compose.

Purpose

The pipeline is the first half of psxGPT. It takes one uncertain PDF and turns it into checked SQLite rows, searchable page text, and links back to the exact source pages. The course version follows one annual report end to end so every decision, file, and failure mode can be inspected.

Every step leaves evidence

Skip manifest, repair manifest, extraction markdown, QC report: these are not clutter. They show what the system believed before a value reached the database.

The page stays attached

Page links are threaded through every stage from OCR to database row. By publish time, every extracted value carries a source_pages field pointing to the filing page it came from.

Mistakes become cases

A missed page, row slip, sign error, or bad field mapping becomes a labeled example. That is how the next prompt, model, or rule change gets tested instead of guessed.

The pipeline is a budgeting system as much as an extraction system. It spends cheap effort first, escalates only when uncertainty remains, and keeps enough evidence for a human to understand why.

Models & cost per page — escalate spend as the population shrinks

Four models, deliberately ordered: a cheap reader on every page, free gates that drop pages for $0, a cheap LLM on the survivors, a more capable, pricier model only on the ~6 statement pages that matter, and a vision model only when QC catches an error. Design Choices

Skip only the obvious misses

The first filters should remove pages we are confident we do not need, such as blanks or clearly irrelevant covers. If we skip the one page with the real value, the later stages cannot recover it.

Use confidence to avoid false certainty

The page tagger will sometimes be unsure. Confidence scores let a page stay in play even if it is not a perfect match. Extra pages cost tokens; missing the real statement page breaks extraction.

Narrow only when the next stage needs it

A broad review is useful early. Exact page boundaries matter only when the extractor is about to spend real context on statement pages.

Use checks as routing signals

If the balance sheet does not balance, that is not just a red mark. It helps decide whether to repair markdown, re-OCR the page, try a stronger model, or inspect the source manually.

1. OCR To Markdown 💲 Mistral OCR · $0.0020/pg

At the start, the pipeline does not know whether the PDF is born-digital, scanned, mixed, or table-heavy. The first job is not to extract final numbers. It is to create a representation that preserves enough structure to inspect and route the page.

ChoiceReason
Use Mistral OCR firstIt gives a consistent per-page markdown representation without asking the model to understand the whole filing.
Use markdown, not plain textPipe tables preserve row and column boundaries that plain text collapses.
Do not ask OCR for final JSONAt OCR time we do not yet know page role, statement type, unit scale, or whether the table is reliable.
Split into page PDFsPage PDFs are later used for source URLs, re-OCR, and source-panel citations.
Markdown is a working representation. It keeps tables, headings, units, and signs visible enough for later stages without forcing OCR to make final accounting judgments.

2. Free Deterministic Gates

Before spending model calls, remove only the pages code can safely identify as non-useful. The goal is not to classify the filing. The goal is to avoid spending on pages where the answer is obvious.

Each gate is pure string/character math on the OCR markdown — zero model calls. Here is exactly what the code computes and the threshold it compares against (stage1_ingest/Step7_BuildSkipManifest.py):

GateWhat the code computes (the signal)Triggers when → consequence
Edge / coverthe page's index within its filingfirst 2 or last 2 pages of the document → skip
Blanklength of the body after stripping the <!-- Page n --> comment< 20 chars → skip
Empty tablechars left after removing pipes | and whitespace< 20 chars — only table scaffolding, no values → skip
Image-onlyimage-tag count, plus content_chars = text left after stripping page-comment, ![]() image tags, heading markers and whitespace≥ 1 image and content_chars < 40 → deferred, not dropped: queued for vision triage instead of skipped (⬜ intended — current code still skips; see the correction below)
Heading-onlythe same content_chars, with zero image tags0 images and content_chars < 40 — a bare section divider → skip
Thincontent_chars< 150 (THIN_CONTENT_THRESHOLD) — too little to produce reliable search_text → skip
Urdu-heavyASCII ratio = (chars with ord(ch) < 128) ÷ total, computed on content only — pipes and whitespace are stripped first so table scaffolding doesn't inflate itratio < 0.85 (ASCII_THRESHOLD) — page is mostly non-Latin (Urdu) script → skip
Decision order (first match wins, so each gated page gets a precise reason): corrupted → edge → blank → empty_table → image_only → heading_only → thin → urdu. Every reason means skip except image_only, which under the corrected contract routes to vision triage.

Why ASCII ratio, and why strip the pipes first

<!-- Page 47 -->
| اثاثے | 2024 | 2023 |
|:---|---:|---:|
| نقد اور بینک بیلنس | 1,250,000 | 980,000 |

raw ASCII ratio (with | and spaces)  -> 0.71   (pipes/digits inflate it)
content-only ratio (strip | + space) -> 0.38   < 0.85  => urdu, skip

The pipes, spaces and Latin digits in a markdown table push the naive ASCII ratio up. Stripping | and whitespace first leaves the actual words, so an Urdu balance sheet reads as ~0.38 and is correctly gated, while an English table stays well above 0.85.

The skip manifest should be conservative. If a page might contain source evidence, keep it available for later routing or re-OCR.
Design correction (Jun 2026) — image-only pages are deferred, not dropped. The image-only gate violates the rule above as currently coded: a chart-only exhibit (a "Key Highlights" page where every figure lives inside an image) is skipped even though it carries data, because OCR recovered fewer than 150 text characters beside the image. The corrected contract keeps the gate's deterministic detection role but changes its consequence: detected pages go to a triage step that decides which carry data worth a vision read; those get a vision OCR pass and re-enter review as ordinary markdown — summary, tags, search_text, and the same downstream QC. Only decorative imagery is skipped. Spec status: ⬜ intended (PIPELINE_SPEC.md §3/§5); the code still skips today.

3. LLM Page Review 💲 DeepSeek V4 Flash · ~$0.0004/pg (est)

The page reviewer reads surviving markdown pages and creates working notes: a short summary, possible page tags, confidence scores, and an extraction quality score. These tags are not final truth. They are routing evidence for later stages.

Tags are routing evidence

The final query engine does not directly use these tags. They help decide which pages deserve more expensive extraction.

Confidence keeps the choice flexible

A 0.55 statement score is not automatically wrong. It is a clue that gets combined with headings, table shape, nearby pages, and table-of-contents hints.

Extraction score routes repair

OK passes, Fix tries markdown repair, ReOCR spends on PDF-page OCR only where needed.

Summaries help later debugging

When an extraction misses a value, summaries make it faster to inspect why a page was included or excluded.

4. Page Shortlists

The page shortlist is the bridge between broad page review and expensive structured extraction. This is where the pipeline admits uncertainty instead of pretending the page tagger was exact.

page_score =
    tag confidence from page review
  + deterministic heading/table evidence
  + nearby-page window
  + table-of-contents anchor
  + prior repair/check signal

The production code already has parts of this loop. The course should make the intention explicit: the shortlist is routing evidence for the locator and extractors, not a final verdict on what every page is.

Measured (Jun 2026): a full-corpus audit (202,831 pages vs the production statement-page maps) showed statement-page identification is a per-filing selection problem, not per-page classification. Per-page keyword tagging scored 24–41% precision — every note that says "charged to statement of profit or loss" matched. The deterministic per-filing selector now in code (Step0_DeterministicPageTagger.py v2: normalized title matching + structural cell evidence + numeric-table density + note-heading and auditor-report penalties + ±2-page adjacency + top-4 per filing with confidence) measures 96–99% filing-level hit rate (PL 99.3 / BS 96.1 / CF 99.4); only 31 reference pages in the whole corpus have no candidate at all, and every extra selection falls in a filing where the locator pinned other pages. The intended division of labor: the deterministic selector proposes, the review-pass tags cross-check, and the LLM locator adjudicates only disagreements over a small candidate set (spec §3 ⬜ intended; wiring it into the stage-3 chain is the remaining step).
This is the tradeoff: extra pages make the next prompt longer, but missed pages can make the statement impossible to extract.

How each extractor's prompt is built — fact / instruction / schema

Every LLM stage assembles its prompt from a context pack under context/<stage>/, split by concern. Code never hard-codes the prompt; it reads the pack via pipeline/shared/prompt_packs.py (order: instruction → schema → fact). So a prompt fix is a markdown edit, not a code change.

fact.md

Stable domain truth — the canonical-field mappings the model must know. "Dividends paid to owners of the parent → dividends_paid; to non-controlling interests → dividends_paid_nci."

instruction.md

Tunable rules — the procedure. "Economically distinct lines get distinct canonicals; never merge two different items under one name."

schema.md

The output contract — the markdown table shape, columns, and formula-reference convention the QC step will verify.

Worked example — the dividend-yield bug. Holding companies report two dividend lines in the consolidated cash flow: dividends paid to the parent's own shareholders, and dividends paid to non-controlling interests. Both were mapped to one canonical (dividends_paid), so on the shared grain the small NCI line overwrote the real owner dividend — and reported dividend yield collapsed (MEBL showed ~0.1% instead of ~5.6%). The fix was a fact edit: add dividends_paid_nci as a distinct canonical so both lines survive, and exclude NCI from the yield numerator. No extractor code changed.

7. Quality Checks And Repair 💲 deterministic QC $0 · vision re-read Gemini 3.1 Flash Lite ~$0.003/err pg

AI extraction can look plausible while still being wrong. Deterministic checks use financial structure to expose likely errors. Their output is not just pass/fail; it is a routing signal for what to fix and how much to spend.

QC is a gate at every stage, not a single step

Every stage that produces data is followed by its own QC. The chain advances only if the gate passes; on failure you fix the cause and rerun that one stage with --only. Statement extraction has three QC layers, cheapest first:

LayerWhenChecksScript
Formula QC (deterministic)after extract, on the markdownRef formulas add up; subtotals match; columns alignedqc_extract_* (Step4)
Semantic QCafter JSONify, on the JSONstatement-level sanity; assets = liabilities + equityqc_json_* (Step6)
Derived QCafter derivecomparative-period match; LTM consistencyqc_comparative_match, qc_ltm (Step8)
loop per stage:
  produce artifact  ->  run QC gate
       PASS -> next stage
       FAIL -> fix cause (pack edit, or repair ladder OK -> Fix -> ReOCR)
            -> rerun this stage:  run.py --only <stage>

Escalation ladder (cheapest fix first):
OK     -> no extra spend
Fix    -> markdown repair via DeepSeek V4 Flash   (cheap text call, ~$0.0004/pg)
ReOCR  -> vision re-read from source PDF via Gemini 3.1 Flash Lite (~$0.003/pg)
persists -> manual gold case for later prompt/model work

What a formula failure looks like — and why it matters

# AGHA quarterly 2024-03-31 — operating_profit check FAILED

  Column: 9M Mar 2024
  Formula: J = E + F + G + H + I

  Components retrieved:
    E  gross_profit:       1,224,094
    F  other_income:        -241,198
    G  admin_expenses:      -251,411
    H  distribution_cost: -3,379,887
    I  finance_cost:      -3,872,496
    ─────────────────────────────────
    Sum of E–I:           -6,520,898   ← what J should be

  Extracted J (operating_profit): -2,648,402   ← what was extracted
  Difference: 146%   ✗ FAIL

  Diagnosis: components add up correctly, so the component rows are right.
  The subtotal J was pulled from the wrong row — a row slip.
  Next: rerun with larger page context or re-OCR page from source PDF.
The formula check is a routing signal, not just a red mark. When components sum correctly but the subtotal is wrong, the extractor read the wrong row (row slip). When components are off too, the issue is column-level corruption or an OCR artifact. Different root cause, different repair, different cost.
QC resultWhat it provesWhat it does not proveExtra spend
PASS Formula equations hold within 5%. Balance sheet equation holds. Every line item is correct. No OCR errors survived. No sign errors exist. None
Fix Minor markdown misalignment detected. Text repair will produce correct extraction. One text-repair pass — no model call
ReOCR Source page needs fresh reading. Vision model will resolve it. One vision model call per flagged page
Fail, persists Automated repair exhausted. Anything — needs human inspection. Manual gold case + future evaluation
QC provides a floor of quality, not a ceiling. A passing QC means the accounting equations held. It does not mean every line item is correctly mapped, every sign is right, or every subtotal is from the right column. Errors that slip through get caught with usage and fed back as gold cases.

Keyword Search Text 💲 DeepSeek V4 Flash · ~$0.0004/pg (est)

The pipeline also creates compact search_text fields so keyword search works better without starting with embeddings. This is generated once per useful page, then reused cheaply by the query engine.

The design choice is deliberate: spend one model call to produce a dense, keyword-rich summary, then run cheap BM25 search over those summaries. Embeddings may become useful later, but keyword search over good summaries is simpler to inspect and easier to debug.

Gold Sets For Ingestion

Status: planned, not yet run. No gold sets are labeled and no optimizer pass has been executed. This section describes the target state, not current behavior.

Gold sets are the input to a prompt optimizer: you cannot optimize a stage's prompt without a labeled set of correct inputs and outputs for that stage to score against. That is the bootstrapping dependency — building the gold I/O for the stage that needs optimization has to come first. The natural seed is the failures that hurt most: missing statement pages, wrong page boundaries, row slips, sign errors, and field mappings.

Gold setWhat it provesPriority
statement_page_goldThe locator can pin exact profit and loss, balance sheet, and cash flow pages.First. Page-boundary misses are recurring and high-impact.
classification_goldPage review produces useful tags and confidence scores.Second. Useful once the locator target is clear.
extraction_goldExtracted values match known-correct source values.High, but more expensive to label carefully.
quality-check_failure_goldKnown row slips, column shifts, and OCR failures trigger the right repair path.Build from failures over time.
Once they exist, gold sets are the durable asset: each production failure that reveals a new class of mistake becomes a labeled case, and the optimizer scores prompt/model changes against it instead of guessing. Until then, prompt fixes are made by hand as fact / instruction edits.
